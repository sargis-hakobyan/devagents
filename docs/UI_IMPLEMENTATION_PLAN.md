## Stack

- **Frontend:** Vite + Preact + TypeScript under `ui/`, built to `ui/dist` and copied into `dist/ui` by `npm run build`. Preact escapes text by default, is small, and needs no runtime beyond the bundle. Routing with `preact-iso` (history routing under `/ui/`). No UI component library, no CSS framework: one hand-written stylesheet with the tokens from `design/ui/README.md`. No remote fonts or scripts; a system font stack stands in for the design's Plus Jakarta Sans.
- **Backend:** unchanged Node/TypeScript service. The built UI is served by the existing HTTP server on the existing port, same origin as the API, in native and Docker modes. No second user-managed frontend service; the Vite dev server is a developer convenience only (`npm run dev:ui`, proxying API calls to a running service).
- **Tests:** Node test runner for API, session and domain tests (`npm test`, no browser needed). Playwright for browser workflow tests (`npm run test:ui`) against a clearly labelled development fixture service with the deterministic fake engine; requires a one-time `npx playwright install chromium`.

## Browser session and CSRF

- **Bootstrap:** `devagents ui [--open]` (CLI, bearer-authenticated) calls `POST /ui/bootstrap`, which mints a single-use code (32 random bytes, 10-minute expiry, consumed on first use) and prints `http://127.0.0.1:<port>/ui/login?code=…`. `--open` tries the OS opener; otherwise the URL is printed, which is the headless path. `serve` never prints codes; the long-lived CLI bearer token never reaches the browser.
- **Exchange:** `GET /ui/login?code=…` validates and consumes the code and sets `devagents_session` as an `HttpOnly; SameSite=Strict; Path=/` cookie (no `Secure` on plain local HTTP; set when `DEVAGENTS_HTTPS=1` later). Sessions live in memory: 12 h idle expiry, 24 h absolute; a service restart ends every session and the user mints a new link. Replay of a consumed code is rejected with 403.
- **CSRF:** every session has a CSRF token. `GET /ui/session` returns `{authenticated, csrfToken, expiresAt}` for same-origin requests. State-changing routes authenticated by cookie require `X-CSRF-Token` equal to the session's token; a bad or missing token is 403. `POST /ui/logout` destroys the session.
- **Host and Origin:** cookie-authenticated requests must carry a `Host` in the loopback allowlist for the configured port (`127.0.0.1`, `localhost`, `[::1]`) and, when `Origin` or `Sec-Fetch-Site` is present, it must be same-origin. Anything else is 403, even from another localhost port. Bearer requests keep today's rule: any `Origin` header is rejected, so the CLI path is unchanged.
- **Static assets and CSP:** `/ui/` and `/ui/assets/*` are served from the built bundle with `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; font-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`. The shell HTML is public; every data route requires a session or bearer.
- **Untrusted content:** task requests, plans, evidence, diffs and agent instructions are rendered as text nodes only. No Markdown rendering in U1, no raw HTML, no links or images generated from content. Evidence entries are bounded server-side.

## API changes (U1)

- `GET /tasks?limit=&before=&projectId=&state=` cursor pagination by row id (default 50, max 200); repeated state parameters are ORed before pagination. Returns summaries, `nextBefore`, and project-wide state counts independent of the current page/state filter.
- `GET /tasks/:id/events?after=&limit=` and `GET /tasks/:id/evidence?after=&limit=` with sequence cursors so polling appends without duplicates; evidence text is previewed at 16 KB with `truncated: true` and a separately bounded metadata projection retaining execution facts, and `GET /tasks/:id/evidence/:sequence` returns one entry bounded to 1 MiB.
- `GET /overview`: counts by state, attention items (awaiting mode, awaiting approval), the active task with its work items, recent outcomes. Each category is queried independently before limiting; execution is also separated from queued work so old running tasks cannot disappear behind new submissions. Attention previews link to the full filtered list. All counts cover the store, not a recent-history slice.
- `GET /status`: runtime and credential availability without secrets (Codex installed/version, dedicated profile signed in, vault locked, Claude installed but not enabled), config defaults and limits, service info. Cached for 30 s because it runs `codex login status`.
- `GET /ui/session`, `POST /ui/bootstrap` (bearer only), `GET /ui/login`, `POST /ui/logout`.
- Task detail adds history-derived `approval` status/timestamp; current state alone never implies user approval. Read-only response additions preserve existing fields for the CLI and scripts.

## Shared dependency store — stop rebuilding every task (2026-11-02, revised after review)

Owner decision: tasks must reuse the project's dependencies instead of installing and copying them for every worktree; cleanup is a tidy-up, not a routine. Today `src/engines/codex/preparation.ts` installs with `--config.package-import-method=copy --store-dir <run temp>/store`, so each task copies the whole tree twice (run store plus worktree `node_modules`, 1.5–2.7 GB for the monorepo), and agent-managed setup repeats the same in a per-worktree HOME (`workspaceRuntime` keyed by worktree path).

Review finding F5 (2026-11-02) rejected the first draft's hardlinked installs: `environment.ts` validation refuses files with more than one link, the transfer copies files, the sandbox scan denies hardlinked files in both modes, and shared writable inodes would let one worker change another worker's dependencies mid-validation. None of those protections may be removed. The design below keeps every one of them.

### Isolation contract

1. **An immutable dependency layer per project and validated input set.** Build the complete install layout once under `/data/deps/<project-id>/<layer-id>/`. The key hashes the canonical paths and bytes of all inputs accepted by `environment.ts`: manifests, lockfiles, workspace configuration and patch contents, plus package-manager/version, full Node version and ABI, OS/architecture and the exact preparation options (frozen install, lifecycle policy, package import mode and relevant configuration). Recollect and validate inputs on every preparation, including cache hits; a manifest change with an unchanged lockfile must still undergo frozen-lockfile consistency validation. Build script-free in a private staging directory, validate the tree with the existing hardlink and escaping-symlink checks, then publish atomically. Directories become 0555; ordinary files 0444 and executable files 0555, preserving legitimate executable bits. Handle symlinks separately; never chmod through them. A published layer is never modified.
2. **An isolated prepared view per worktree, with task-local workspace resolution.** Do not symlink the whole `node_modules` into the shared layer: Node resolves real paths, and workspace dependencies would then resolve to the layer's metadata-only directories. Materialize the complete dependency layout in each worktree with filesystem copy-on-write/reflink clones where supported, without hardlinks. Rebase/validate workspace links against that worktree's source directories, retaining pnpm's relative layout. Every real dependency path used by Node stays inside the private view. Existing tree and sandbox validation still apply; this design needs no arbitrary external-symlink exception. If the data-volume filesystem cannot clone, retain the existing isolated copy path and report its physical-byte/time cost. Sharing downloads and the prepared layer still avoids rebuilding the install; do not promise zero copying or zero dependency bytes on that fallback. Npm initially uses the same isolated copy/cache fallback until its clone layout is verified.
3. **Published content remains sandbox-read-only in every phase.** Grant only the exact pinned layer/runtime generation read access, never their parent or write access. Private dependency views may be writable only where the existing phase/role policy permits; extra-rules mode still forbids ignored-file mutation. Keep writable caches and generated output private. The initial candidate list is root and package-local `node_modules/.cache`, `node_modules/.vite`, `node_modules/.vite-temp`, plus each project's declared generated-package paths (including Paraglide where present). Inspect each tool's actual paths, configure output directories or use links contained within the private worktree, and verify realpath behavior before claiming compatibility. Generated package contents requiring lifecycle/native builds use an isolated private build step under the existing setup policy; they never mutate the published script-free layer. Unsupported paths are reported explicitly, with no widening of sandbox access. Manifest/configuration/patch changes invalidate the view input digest as well as lockfile changes.
4. **Explicit identity and immutable tool generations.** Thread a typed `ProjectRuntime { projectId, projectPath, inputDigest, layerId, layerPath, viewPath, runtimeId, runtimePath, privateHome }` through preparation, installers, engines and validators. Build tool generations in private setup staging and publish atomically under a per-project publication lock. Every invocation pins an immutable generation; setup for another worker publishes a new generation instead of changing tools a validating worker can read. Keep HOME, XDG caches and temporary state per worktree, with PATH referencing pinned tool binaries. Adapt `workspaceRuntime`, `nodeToolPath`, adapter and validator together; simply keying today's writable HOME by project would introduce shared state. Never await agent slots, readers, lifecycle drain or another workflow while holding the publication lock; run setup outside it and use a short publish/recheck critical section with deterministic lock ordering.
5. **Agent-managed setup uses a structured preparation request.** Add an explicit request/response contract for dependency/tool preparation and generation selection before replacing today's direct installs; `SetupOutput.ready`/`summary`/`limitations` alone cannot request a rebuild. Preparation validates the request against the actual worktree inputs and returns the pinned identities. Preserve default-mode lifecycle/code-generation support in private views. Native or script-built artifacts may be reused only when their complete inputs and ABI/platform compatibility are represented in a separate artifact key; otherwise rebuild privately. No writer receives an existing published generation as writable storage.
6. **Retention and measurement.** Layers and runtime generations referenced by a worktree or active invocation are pinned. List unreferenced generations in Settings and prune only on an explicit owner action under the publication/pin lock. Measure physical exclusive bytes with filesystem-aware accounting for shared extents; report unavailable when it cannot be determined, rather than summing apparent sizes. Report private-view/cache bytes separately. Run temp data holds no repeated persistent package-store copy; validation-run retention remains a separate policy.
7. **Docker image housekeeping belongs to the launcher.** `./devagents start` removes only images it built itself (its own tags) that are no longer the current build, after a successful build; it never prunes other images, volumes or caches.

Expected savings depend on the data-volume filesystem: reuse eliminates repeated dependency downloads and installation; clone-capable filesystems can also share unchanged dependency extents. Private writes and build output remain per-worktree costs. Measure preparation latency and exclusive bytes before replacing the boards' illustrative figures or claiming a particular saving. These are future preparation changes, not capabilities of the current code.

Verification for that future implementation: two tasks reuse an unchanged install with networking blocked; a source edit in workspace package A is resolved by dependent package B in the same worktree and never by another worker; CLI launchers retain execute permissions; every documented cache/code-generation path stays private. Verify clone-capable and copy-fallback filesystems separately. Manifest-only, workspace-config and patch-content changes invalidate reuse, and inconsistent lockfiles fail frozen validation. Race worker B's setup publication against worker A's validation and prove A sees its pinned tools unchanged. Existing hardlink and external-link attacks still fail. Exercise lock ordering, native/lifecycle builds, npm fallback, runtime retention and per-worktree HOME separation. ### Contracts (revised after review findings F6–F8, 2026-11-02)

1. `GET /status` gains `storage: { measured: boolean; freeBytes?: number; totalBytes?: number; worktreeBytes: number; runBytes: number; finishedTasksHoldingFiles: number }` computed under the existing cache; task summaries gain `footprintBytes?: number` and `uncommittedFiles?: number` for finished tasks (measured lazily and cached per task until cleanup; "not measured" is a value, not an error). Sizes are exclusive bytes.
2. **Active means owned work is still running, not a state-list lookup.** Preview and cleanup require terminal state and `drained(taskId)`: no active slot, worker promise, nested loop/wave/child workflow or owned process-group cleanup can still write. Track live ownership, joining all descendants; persisted child statuses alone are not authoritative after restart. Await drain with a bounded timeout outside the per-task lifecycle mutex, returning `409 task_active` if necessary. Then acquire that mutex and recheck terminal state and live ownership before inventory/deletion. Run, approval and cancellation take the same mutex only for short ownership/state transitions, never for an entire workflow or while awaiting drain; cancellation must be able to signal the work being drained. Revalidation and deletion remain in one cleanup critical section, so no new owned run can start between them. Current cleanup does not yet provide this guarantee.
3. `GET /tasks/:id/cleanup-preview` (session or bearer, read-only) returns a bounded canonical inventory and its digest: worktrees with paths, exclusive bytes and kinds; tracked entries with HEAD/index modes and hashes (all conflict stages) and separately computed working-tree content hashes; untracked entries with path/type/mode/size/content hash; ignored counts/bytes; branch names/tips and intended archive refs; recursive run-directory entries with relative path/type/mode/size/content hash; and recovery-patch availability/size/reason. Porcelain v2 supplies index/HEAD facts, not working-tree content hashes: read and hash the latter explicitly without following symlinks. Bind link target text instead of traversing links. Refuse foreign ownership with `409 cleanup_ownership`. Enforce count, byte and traversal limits before removal; oversized inventories return `413 preview_too_large`, never a partial hash. The HMAC covers this inventory plus task ID using a per-process secret. A same-size tracked/untracked edit, index-only change or new run file invalidates it. Ignored files intentionally bind counts/bytes only, not their contents; show that exclusion. Shared layers/runtimes are outside task removal and are never traversed for sizing or deletion. The mutex excludes service-owned writers, not external local processes; state this residual race and revalidate immediately before removal.
4. `POST /tasks/:id/cleanup` with `{ digest, savePatch: boolean }`: await drain outside the lock, acquire/recheck as above, recompute the inventory, and return `409 cleanup_preview_stale` with a fresh preview on mismatch. Preflight every requested recovery patch and every archive ref before any destructive step. Persist the cleanup operation and all requested redacted artifacts, create and verify archive refs **regardless of `savePatch`**, then remove only inventoried resources through the existing ownership checks. Persist operation progress so restart/retry can reconcile partial cleanup safely, without overwriting a newer branch tip or deleting a recreated path. A completed task's branch is always kept. Never create commits on user branches. Record actual removed/kept resources and measured freed bytes as cleanup evidence. With `savePatch=false`, explicitly disclose that staged and other uncommitted content will be lost.
5. **Recovery preserves staged and working content separately.** Before deleting a branch, create `refs/devagents/archive/<task-id>/<branch>` at the previewed tip, without moving or deleting the original until the archive is verified. Use compare-and-swap ref transactions with expected old tips; refuse conflicting archive names, and allow idempotent resume only when the recorded operation and tip match. Archive creation precedes branch deletion even when patch saving is off. Archive refs reuse existing objects initially but pin them indefinitely: list them and their retention cost in storage accounting, with an explicit owner-controlled prune action separate from task cleanup.

   For each worktree with `savePatch=true`, save two named components: `git diff --cached <recorded-base>` (base to index, including checkpoint changes) and `git diff` (index to working tree). State the task/item base SHA and restoration order; a base A, staged B, working A must preserve both transitions. Refuse conflicted multi-stage indexes before deletion with a useful manual-export explanation rather than silently dropping stages. List and exclude untracked and binary content. Redact both textual components before persistence; keep only one redacted copy of each, with raw output transient, and disclose when redaction changes context. Never label these artifacts a clean-apply backup. Enforce a combined 4 MiB bound per worktree, including exclusion metadata; oversized content returns `413 patch_too_large` for the whole request before deletion instead of silently dropping large hunks. Identify the worktree, recorded base and proposed archive refs for manual export; do not imply archive refs already exist on a preflight refusal.

6. `GET /tasks/:id/patch` returns the saved component pairs as text with their base commits, component names and restoration order; `GET /tasks/:id/patch/download` serves them as `text/x-patch` with safe filenames, addressed by task identity only.
7. The bulk bar calls the per-task preview and cleanup routes; there is no bulk endpoint. A refusal for one task leaves the others done or untouched and the bar reports which.
8. CSRF, Origin, Host and the bearer rule apply to the new mutation as to every other. The browser never sends paths, refs or branch names.

### Verification

Exercise archive collisions, concurrent tip changes, crash/retry between every durable step, and explicit archive pruning/accounting. Stale, forged, cross-task and replayed digests refuse; cover same-size tracked/untracked edits, staged-only changes, conflict stages and recursive run-directory changes.

## U6 handoff — the Work tab as a team board (2026-11-02)

Design: `design/ui/U6-Work-Team.dc.html` (fifth canvas row). Owner decision: the Work tab shows the team on this task, who is finished, who is working and who is left, as two components. Nothing else on the board is a separate screen: the roster-state cards, the opened stack, the five-failures card, the 390 px drawing and the notes are states of these two components or guidance. The three-column roster layout drawn on the board is **not** built; the ordered member list replaces it. No pan-and-zoom canvas of any kind.

### Components

1. **Pipeline** ("Your team on this task"), at the top of the Work tab, replacing today's "Measured: …" line. Stages left to right: Plan, Build, Review, Integrate, Commit; single-item tasks have four stages (no Integrate). Each stage shows its title, a stage chip ("✓ Done", "▶ 2 of 3 done", "▶ Working", "Up next", "✕ 5 stopped") and the members who do it: avatar (role glyph in an ink circle), status ring, status badge, name, and one or two measured lines. Connectors between stages turn green when the earlier stage is done. A legend (Finished, Working now, Up next, Needs you) sits in the header. A footer line names members the plan does not need ("Not needed for this task: QA Engineer").
2. **Member list**, below the pipeline, replacing today's work-item cards. One card per involved member, ordered needs you → failed → working now → up next → finished → not needed. A card carries the avatar, name and id, the assignment line (item ids and titles, owned paths, dependencies), the existing stage chips (Implemented ×n, Tests ✓ / ✕ then ✓ / ✕ exit n / output truncated, Review ✓ 0 findings / n findings, Checkpoint sha, Integrated), timing (started → finished, or elapsed while working, from recorded timestamps), repairs used of the budget, and "Show activity for <item>" which switches to the Activity tab filtered to that item. A member with several items has one card that lists them; the current item cards disappear.

Status rings and badges: finished green ✓; working blue ▶ (↻ while repairing); up next grey dashed …; needs you amber ! (the "You" member); failed red ✕; aborted or interrupted grey ⚠; not needed light grey –. Status is always ring + badge + text; colour never carries meaning alone.

### How status is derived (no new backend field)

Inputs the page already loads: `GET /tasks/:id` (state, approval, plan, `agents` roster snapshot, `team`, outcome), `GET /tasks/:id/items` (per-item state, agentId, repairCycles, commit, updatedAt, error) and the evidence log (`run-started`, `run-completed`, `run-failed` with `runId`, `phase`, `agentId` and `workItemId` for per-item runs; `validation`; `item-commit-created`; `commit-created`; `limitations`). Put the derivation in one pure module (`ui/src/team-board.ts`) with unit tests; the components only render its output.

- **Members**: the roster snapshot, in roster order; "You" is added as a member while the task is `awaiting_mode` or `awaiting_plan_approval`; "DevAgents" is the Commit stage member. Involved = planner (the agent of the planning run), every `assignedAgent` of a plan item, the integration agent, every agent with a review run; everyone else is "not needed" with the reason "no item asks for <capability>" when a capability can be named, otherwise "not assigned by the plan".
- **Plan stage**: the planning agent; done when a plan is stored; the line shows the plan version, item count and planning run duration; in plan-approval mode a second line "You approved HH:MM:SS" or "Waiting for your approval".
- **Build stage**: one row per implementer with its items; row status from the items' states (pending → up next; creating/running/validating/reviewing/checkpointing/integrating → working, repairing → working with ↻; reviewed/completed → finished; failed → failed; aborted/interrupted → aborted; cancelled/blocked → not needed-style grey with the reason). Stage chip counts items, not members.
- **Review stage**: the reviewer; counts item reviews approved and findings; working while a review run is open; done when the final review approved; "Next: item c, once its tests pass" while idle with work still coming.
- **Integrate stage** (multi-item only): the integration agent; up next until the integration run starts; working during it; done when combined validation passed.
- **Commit stage**: DevAgents; done when `outcome.commit` exists with the short sha and time; "No commit" on failure or cancellation.
- **Durations** are differences of recorded timestamps, summed over a member's runs including repairs; a run still open shows elapsed from its start. Never estimate; show "—" when no timestamp exists.
- **Repair** reopens a stage: while a repair cycle is open the Build stage and the member are working again, never finished.

### Fold rule

Each pipeline stage shows up to four full rows and the member list up to six; a finished task's list never folds. Past the limit, finished rows fold first into a stack, then up-next rows; working, failed and needs-you rows never fold. A stack is a button: up to five overlapping small avatars, the stage chip ("✓ 6 finished · 7 items"), one line of detail and "Show"; it expands in place with a "Hide" bar and the open state is kept per task in `localStorage` only. A stack is reachable by keyboard and announces its count.

### States to cover

Single item (four stages, reviewer working); multi-item running (fixture "Three modules": a and b integrated, c validating); awaiting mode and awaiting plan approval ("You" with the existing approve, reject and mode controls, other members "waiting for you"); completed (everyone finished, commit sha); failed (stopped member with its finding and repair count, finished members, members that did not get a turn); cancelled and interrupted (grey ⚠ rows with the recorded reason); large team (ten members, twelve items, folded and opened); five failures at once (the stage grows); narrow width (stages stack vertically, member cards full width; no horizontal scroll at 390 px).

### Verification

- Unit tests for the derivation module: every state above from recorded evidence fixtures, repair reopening, durations from timestamps, "not needed" reasons, the fold rule at the threshold (4 and 5 rows, finished before up next, failures never fold), "You" only in the two awaiting states.
- Browser tests on the fixture: pipeline stage count for single and multi-item tasks, status text per member, stack expands and the state survives a reload, 390 px has no horizontal scroll, the activity link filters the Activity tab.
- Hostile fixture text (item titles, agent names) renders as text.
- `npm run check` and the browser suite pass; no backend change, no new dependency, no model call.

### Out of scope

The three-column roster, any zoomable canvas, a dependency graph view, drag-and-drop, the Overview active-task cards (unchanged), the Plan tab (already redesigned), and the U4/U5 work.
