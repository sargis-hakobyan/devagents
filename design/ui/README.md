# DevAgents browser UI — design source

Static design boards for the local browser UI described in `docs/FRONTEND_BRIEF.md`. They are mockups, not the application: nothing here is served by the service or shipped in the image.

## What is here

- `canvas.json` — the canvas index: every board's file, frame position and size, and canvas notes.
- `Main.dc.html` and `A-*.dc.html` — **Direction A, the chosen direction**: dark indigo band with an amber spark mark, light lavender-grey workspace, Plus Jakarta Sans. The Overview (`Main.dc.html`) uses a dense two-column structure.

Selected boards: Overview, Tasks, Task detail (running), Teams with the member editor, Projects, Settings, and a states sheet (empty workspace, no teams, missing project, locked connection, unverified model access, loading, disconnected, approval required, failed, narrow 390 px view).

- `U3-*.dc.html` — **U3 extensions of Direction A** (second row on the canvas; the U1/U2 boards above are unchanged): `U3-Register` (project registration with Docker mount and container-path guidance, pending, invalid path, conflict, other backend refusals, registered), `U3-Submit` (task submission with project, request, acceptance criteria, team with unavailable drafts/archived teams, autonomy mode, live resolved summary, pending attempt, unknown outcome with same-key retry, service refusals, accepted with the frozen revision from the response), `U3-Approve` (awaiting-mode choice with no preselection, version-bound approval, stale approval, rejection confirmation, cancellation while running, the non-cancellable committing boundary, after cancellation), `U3-Diff` (read-only diff of a completed task by task identity with complete, binary, truncated, empty, unavailable and redacted states), `U3-Setup` (guided connection setup from secret-free status with copyable terminal commands, locked vault, unverified model access, entry points) and `U3-States` (pending attempt restored after reload, disconnected submission and approval, stale approval, restart, invalid path with preserved input, diff loading, and three 390 px views).
- `U4-Cleanup-*.dc.html` — **free disk space, embedded in the existing screens** (third row; no new page): `U4-Cleanup-Task` (the task header's footprint chip and action button, the Result tab's "Working files" row with the inline preview, patch checkbox, the completed-task variant, the after-cleanup rows and the refusal states) and `U4-Cleanup-Lists` (the Tasks page's "Holding files" filter pill with its bulk bar and per-task previews, the Overview Scheduler card's storage line in low, healthy and not-measured states, and the Settings storage row). Compaction (delete generated directories, keep the worktree, branch and every edit) is the first tier; removal is the second.
- `U5-*.dc.html` — **improvements taken from reviewing Paperclip** (fourth row): `U5-Attention` (the Overview's attention card extended with silent workers and bounded recoveries, the task page's silent-worker and recovery-needed states, and the other attention variants) and `U5-Modes-Cost` (the submit form's work-kind group with an answer-only mode, an answered question on the task page, per-run usage in the Activity tab, task totals, the Overview spend card and an optional project budget). The plan is `docs/IMPROVEMENT_PLAN.md`.
- `U6-Work-Team.dc.html` — **the Work tab as a team board** (fifth row; design only, to be refined with the owner): the task page with two treatments on one screen, a pipeline (plan → build → review → integrate → commit with the members who do each stage, status rings and badges) and a roster (Finished / Working now / Up next columns with the existing stage chips inside the member cards); roster states for awaiting approval ("You" as a member), completed and failed; a 390 px stack; and the single-item pipeline with the reviewer working. A large-team section (10 members, 12 items) shows the fold rule: up to four full rows per stage or column, finished members fold into an avatar stack first, then up-next members, and working, failed or needs-you rows never fold; drawn folded, opened, and with five simultaneous failures. Every value is a recorded run, event or checkpoint; no new backend field is needed.
- `U7-GitHub-*.dc.html` — **GitHub integration** (sixth row; design only, nothing implemented): `U7-GitHub-Connect` (Settings, housekeeping only: connected accounts as single rows with a "Manage" menu and folded details, the empty state pointing to "Add project", and three problem states each with the one thing to do), `U7-GitHub-Projects` (one row per project; "Add project" asks local folder or GitHub repository, picks a connected account or takes a token inline for a new one; "Link to GitHub" for a local project; three autonomy presets with a folded fine-tune; three problem states), `U7-GitHub-Publish` (the Result tab with the unchanged local result followed by the publish card and its states), `U7-GitHub-PR` (the task's Pull request tab: status, next-step banner, rounds, checks and review comments) and `U7-GitHub-States` (Overview attention items, Tasks chips and filter, edge states and a 390 px view). - Available ticket cards now support dragging into Planning to start, with a highlighted drop target and a pending card. Start task performs the same action for keyboard and touch users; clicking the card opens the existing form. Running task positions continue to follow backend state. This extends U10; see the 2026-11-18 drag-to-start decision.
- Tasks started from a ticket (2026-11-18) have no board of their own: the submit form gains one status line and a taller request field, the task page a ticket line and a folded full request, and the Tools mapping a "Reading one ticket" pair under "How the tool is called". These follow the existing components; see `docs/DECISIONS.md`.

Every example value mirrors the deterministic fixtures (project `fixture`, task "Three modules", items a/b/c, the six built-in roles, the U2 fixture teams). Counts and stages are real backend fields; there are no percentages, time estimates or model-availability claims the backend cannot measure. Controls whose contract is still to come (cleanup preview, patch download, browser credential entry, the opt-in paid connection test) are drawn disabled with a reason.

The implemented read-only diff extends the boards with GitHub-style green/red line backgrounds and counts, blue hunk headers and neutral metadata. Patch markers remain visible alongside colour.

The implemented task **Usage** tab adds three compact totals (reported tokens, estimated API cost, API-equivalent estimate), expandable step/attempt tables, missing-data labels and an explicit USD/EUR selector. This extends the cost boards without implementing their project budgets or monthly rollups.

Form action buttons fit their labels and align left, retaining their existing height. On narrow screens, Submit task stays below the form instead of floating over its fields; this supersedes the sticky submit treatment in the U3 boards.

## Editing

Each `.dc.html` file is a self-contained board: plain HTML with inline styles inside an `<x-dc>` wrapper plus a small runtime script. Open a file in a browser to preview it roughly (the `./support.js` runtime is only available on the design canvas, so the `{{ }}` features are unused here and the markup is static).

To reload the whole set on a design canvas, publish `canvas.json` and the `.dc.html` files to a canvas of the Design artifact type with `canvas.json` as the index. Only the selected direction is included in the repository.

When the implementation (U1 onwards) diverges from these boards, update the boards or note the divergence in `docs/DECISIONS.md`; the boards are the reference for the look, the brief is the reference for behaviour.

### Implemented execution timeline — 2026-11-03

The Work tab now separates the team overview, the actual chronological **Execution workflow**, and expandable planned responsibilities. Each agent attempt retains its own card with role icon, real actor name, scope, timing, status text and summary. Amber review findings link to the later developer repair; green means the run finished, while validation and review remain separate evidence. Parallel runs link to their overlapping steps. Updates poll every three seconds, with preserved content and a retry control during failures. The narrow layout wraps names, commands and findings without horizontal scrolling. This supersedes the fixed-stage detailed workflow treatment; the stage overview remains a planning/status summary.

Agent runs alone receive numbered cards. Consecutive automated checks form a compact, initially collapsed disclosure with visible pass/fail counts; individual scopes and commands remain inside. Commit is a compact confirmation. No repeated DevAgents member cards appear for test commands.

Member avatars use consistent rounded line symbols: a hierarchy for the lead, code brackets for developers, a checked document for review, and a flask for QA. The original circular backgrounds and status badges remain. A separate 12 px engine mark sits beside the avatar: a terminal mark for Codex and a terracotta starburst for Claude, with the engine name in a tooltip and accessible label. The team editor uses the same symbols in compact 32 px circular avatars, with tiny engine marks beside them. Desktop workflow columns place each icon pair above the member text to preserve readable line lengths. Folded decorative avatar stacks omit engine marks; expanded rows show them.

The task submission form uses a single request field for the change and expected outcome. The separate acceptance-criteria editor shown in the U3 boards has been removed.

The Plan tab leads with the proposed change, assigned member names, planned verification and user-relevant risks. Branches, commands, file ownership, item descriptions and technical acceptance criteria live under a collapsed **Technical details** disclosure. New plans generate the approval prose in their existing planning call. Older summaries remain unchanged, and plans without verification prose show an explicit fallback pointing to the technical checks. Approval buttons follow the plan in normal document flow so they do not cover its content. This supersedes the expanded implementation-first approval treatment in the U3 boards.
